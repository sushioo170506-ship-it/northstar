# OpenAI GPT-Live：技术路线、竞争差距与模型厂商战略启示

> 资料截点：2026-07-12

## 摘要

OpenAI 于 [2026 年 7 月 8 日发布 GPT-Live](https://openai.com/index/introducing-gpt-live/)，首批包括 GPT-Live-1 与 GPT-Live-1 mini，分别面向 ChatGPT 付费用户和免费用户。它不是已开放的 API 模型，而是驱动新一代 ChatGPT Voice 的产品级语音模型。核心变化有二：一是从离散轮次转向连续全双工，模型说话时仍持续处理输入，并反复判断说、听、停、响应打断或调用工具；二是把搜索、复杂推理和 Agent 工作委派给后台前沿模型，首发使用 GPT-5.5，GPT-Live 自身继续维持对话。

这条路线把语音系统拆成两个时间尺度：前台模型优化百毫秒至秒级的时序和交互控制，后台模型负责秒级至分钟级的推理与执行。语音模型因而不必独自承担全部知识与推理负载，“交互智能”和“任务智能”可以分别迭代。

截至截点，OpenAI 未公布 GPT-Live 的参数量、音频 codec、token 率、训练规模或内部模块，也没有可跨厂商复现的完整评测，不能根据演示反推其结构。国内模型在语音理解、中文知识、方言、表达控制和端侧效率上已具竞争力；有条件地看，主要差距更可能集中在连续全双工时序、真实交互数据闭环、后台委派与 Agent 执行可靠性、安全运营及大规模产品反馈。由于缺少同版本、同条件第三方评测，这是一项证据受限的战略判断，而非确定排名。

## 研究对象界定与产品定位

GPT-Live 必须与四个相邻概念分开。

第一，**GPT-Live-1/mini 是 ChatGPT Voice 产品模型**。付费计划默认使用 GPT-Live-1，免费计划使用 mini；首发覆盖 iOS、Android 和 ChatGPT.com，不支持视频、屏幕共享、Connected Apps、插件、Codex、Work、自定义 GPT，也未进入 Business、Enterprise、Edu 工作区，详见 [ChatGPT Voice 帮助文档](https://help.openai.com/en/articles/20001274-chatgpt-voice)。官方只称计划带到 API，因此截至 2026-07-12 尚不能通过 API 调用 GPT-Live。

第二，**GPT-Realtime-2/2.1 是 API 模型，不是 GPT-Live**。OpenAI 于 [2026 年 5 月发布 GPT-Realtime-2](https://openai.com/index/advancing-voice-intelligence-with-new-models-in-the-api/)，定位为带推理、工具调用和语音输出的实时 Agent 模型；[模型页](https://developers.openai.com/api/docs/models/gpt-realtime-2)公开 128K 上下文、32K 最大输出以及音频、文本、图像输入。7 月 6 日公告称 gpt-realtime-2.1 改进字母数字识别、静音、噪声及打断，并通过缓存使 Realtime 语音模型 p95 延迟至少降低 25%；该信息来自[官方社区公告](https://community.openai.com/t/new-realtime-models-on-the-api-gpt-realtime-2-1-and-gpt-realtime-2-1-mini/1385896)，并非 GPT-Live 规格。帖中 2.1-mini 在某 SIP 流程未触发工具的描述只是单个社区经验。

第三，**Realtime API 是会话和传输平台**，承载 WebRTC、WebSocket、SIP、事件、工具和状态；GPT-Realtime 系列是其模型。GPT-Live 将来是否沿用相同接口、暴露何种全双工事件，尚未公布。

第四，**Advanced Voice Mode 是上一代产品体验**。它以单模型直接处理和生成音频，但仍以静音划分离散轮次；Standard Voice 则是 STT—LLM—TTS 级联。GPT-Live 持续处理输入输出，但首发尚未覆盖 Advanced 的视频和屏幕共享，不能视为所有旧能力的即时超集。

因此，GPT-Live 的定位不是单纯“更强的语音模型”，而是 ChatGPT 的实时交互控制层。竞争单位也从 ASR、TTS 或单轮问答，转向长时间交谈中能否正确分配话权、保持在场感、掩蔽后台等待、完成任务并安全退出。

## 技术路线与系统架构

### 从轮次识别到连续时序决策

传统级联系统依次执行识别、推理和合成，模块可替换、文本易审计，但累计延迟较高且会丢失语气、节奏等副语言信息。端到端语音模型减少了模块边界，但若仍依赖静音判断轮次，用户停顿、填充词、背景人声或临时改口仍会引发抢话。

GPT-Live 在说话时继续接收输入，可选择继续听、给出“嗯”等 backchannel、开始或停止输出、接受打断、调用工具。“是否说话”由此成为持续的语义时序决策，而不只是外围 VAD 阈值。困难不在双向传输本身，而在根据语义、韵律、停顿和上下文判断话权。

[Moshi 论文](https://arxiv.org/pdf/2410.00037)较早展示了联合建模用户与系统音频流的全双工框架，并报告 160ms 理论延迟。它证明多流建模、内在文本表征和流式 codec 是可行路线，但只能作为学术先例，不能证明 GPT-Live 使用同类 codec、token 布局或网络结构。

### 交互模型与深度工作解耦

当请求需要搜索、复杂推理或 Agent 能力时，GPT-Live 将工作委派给 GPT-5.5；后台尚未完成时，前台仍能交谈和接收补充条件，结果返回后再自然接续。Instant 首发使用 GPT-5.5 Instant，Medium 和 High 使用不同推理强度的 GPT-5.5 Thinking，均为 OpenAI 官方披露。

据公开功能，可抽象出媒体传输、持续交互状态、委派控制、后台模型与工具、结果回流、安全监控六层；这是功能推断，不是官方内部架构。其优势是实时性与智力规模解耦，代价是状态管理显著变难：委派期间用户可能改口、取消、提出新任务，系统必须处理任务身份、并发、依赖、陈旧结果和非幂等操作。

端到端体验还取决于客户端回声消除、网络抖动、播放控制和服务调度。有关 WebRTC 的 [Hacker News 讨论](https://news.ycombinator.com/item?id=48051951)显示，工程师对低延迟与可靠性的取舍存在分歧，也有匿名生产经验称从约 1200—1500ms 降至约 700ms 后用户困惑和放弃减少。这些不是受控实验，只能说明模型首包延迟不能代表完整体验。

## 能力边界与可靠性

OpenAI 称，在匹配的 5—10 分钟对话中，GPT-Live-1/mini 相比 Advanced Voice Mode 在整体偏好、轮次、打断、对话流和自然度上被明显偏好；GPT-Live-1 在 GPQA、BrowseComp 和内部版本 τ³-Voice Telecom 上也更好。发布页正文主要作定性陈述，图表才承载更多数值，且未公开足以独立复现的样本、提示、裁判设置和置信区间。因此这些结果只能证明在 OpenAI 自设条件下相对上一代有明显产品改进，不能证明跨厂商全面领先。

### GPT-Live 官方能力评测

下表汇总 OpenAI 发布材料中的能力对比。需要特别说明数据链路：盲测偏好及基准精确值由 [The Decoder 对 OpenAI 官方图表的二手转录](https://the-decoder.com/chatgpt-can-now-listen-and-talk-at-the-same-time-making-ai-conversations-seem-more-human/) 提供，原始发布页正文没有逐项列出全部精确数字。它忠实指向官方图表，但仍是二手报道，不是独立团队重新运行模型所得，因而不可当作独立复现。表中的 “High” 与 “Instant” 是委派给 GPT-5.5 时的推理档位，不代表 GPT-Live 前台模型单独取得相同知识或搜索成绩。

| 评测项目 | GPT-Live-1 | 对照 | 结果含义与限制 |
|---|---:|---:|---|
| 匹配对话盲测总体偏好 | 75.7% | AVM 为被比较对象 | 用户在约 5—10 分钟匹配对话中二选一；是厂商组织的主观偏好，不是事实正确率 |
| Conversation flow | 4.96 | AVM 3.80 | 衡量对话流体验；未披露足以复算的完整量表、样本构成与区间 |
| GPQA，High | 84.2% | AVM 45.3% | 科学推理准确率；High 包含 GPT-5.5 后台高强度推理的贡献 |
| BrowseComp，High | 75.2% | AVM 0.7% | Agent 式网页检索准确率；主要反映后台搜索和委派系统，而非前台语音模型独立浏览 |
| τ³ Voice Telecom，High | 约 65% / 约 385 秒 | AVM 约 30% / 约 385 秒 | 内部电信客服任务的成功率/耗时，图表读数为近似值 |
| τ³ Voice Telecom，Instant | 约 37% / 约 225 秒 | AVM 约 30% / 约 385 秒 | Instant 成功率低于 High 但耗时更短，展示质量—等待时间权衡 |

这组数据支持三个较窄的判断。第一，75.7% 的盲测偏好和 4.96 对 3.80 的对话流分数，与“连续听说、减少抢话”的产品目标一致，但主观评分会同时受声音、人设、延迟和回答内容影响，不能单独归因于全双工架构。第二，GPQA 从 45.3% 到 84.2%、BrowseComp 从 0.7% 到 75.2% 的跃升，方向上验证了前台语音交互与后台前沿模型解耦的价值；由于 High 档调用 GPT-5.5 Thinking，这不是 GPT-Live 独立基础智力的同模型升级。第三，τ³ Voice Telecom 的 High 与 Instant 展示可调节的帕累托取舍：前者约多完成 28 个百分点，但相对 Instant 多用约 160 秒。由于 τ³ Voice Telecom 是 OpenAI 内部版本，且“约”值来自图表读取，不能与其他公开客服榜单直接横比。

公开边界包括：部分语言仍可能有非母语口音或流利度缺口；主要面向一对一，多人发言可能误触发；重叠语音、背景噪声、麦克风与网络仍影响理解和打断；对话转录并非逐字记录；首发不支持实时视频、屏幕共享和广泛连接器；GPT-Live 自身没有代码执行能力，也缺少广泛独立工具访问，复杂工作的能力随委派模型和工具变化。

可靠性不能只看回答质量。语音 Agent 要同时正确理解意图、判断何时行动、调用并验证工具、准确播报状态。“我来查一下”不等于工具已执行；“已提交”也不同于外部系统最终成功。预约、支付和设备控制等非幂等动作必须区分计划、确认、调用、提交与成功，并支持取消和补偿。

安全方面，OpenAI 称系统会持续检查输入和生成输出，可引导或中断回复、播放提示、提供文字资源或结束会话。测试覆盖自伤、精神病性内容、情感依赖、暴力、色情、未成年人声音、模仿、诈骗和音频扰动。安全能力应理解为模型训练、流式监控、账号执法和长期运营的组合，而非单一分类器。

### GPT-Live System Card：完整安全结果

[GPT-Live System Card 官方 PDF](https://deploymentsafety.openai.com/gpt-live/gpt-live.pdf)只聚焦此次语音上线的安全训练、语音原生评测、红队和 Preparedness Framework 判断。它不是披露参数量、codec、训练算力、网络模块或通用能力全景的架构/通用能力系统卡；不能因为名称是 System Card，就把未披露的模型结构或能力细节视为已经公开。

第一张表使用经授权分享并经过权限、退出/删除状态检查、PII 清理与去标识处理的真实用户音频。研究者转录提示、生成回复并评价安全性。列顺序严格保持为 AVM、GPT-Live-1、AVM mini、GPT-Live-1 mini。

| Production prompts 类别 | AVM | GPT-Live-1 | AVM mini | GPT-Live-1 mini |
|---|---:|---:|---:|---:|
| Sexual | 0.96 | 0.97 | 0.97 | 0.95 |
| Illicit behavior | 0.74 | 0.97 | 0.60 | 0.94 |
| Mental health | 0.90 | 0.90 | 0.78 | 0.84 |
| Personal data | 0.96 | 0.96 | 0.95 | 0.95 |
| Emotional reliance | 0.88 | 0.82 | 0.78 | 0.78 |
| Self-harm | 0.89 | 0.96 | 0.81 | 0.92 |

这里的 “Production prompts” 容易被误读。它们虽来自真实生产音频，却不是按真实流量类别占比加权的线上安全率，而是围绕现有 AVM 尚未理想回答的案例建立的对抗性难例集。因此不能据 0.74 推断真实使用中有 26% 的违法行为请求处理失败，也不能用各行简单平均估算总体安全水平。GPT-Live-1 的 Emotional reliance 从 0.88 降至 0.82，GPT-Live-1 mini 的 Sexual 从 0.97 降至 0.95；官方明确称这两项变化均无统计显著性，不能据点估计宣布安全能力实质回退。相对更大的 Illicit behavior 提升——0.74→0.97 和 0.60→0.94——值得关注，但仍只适用于该困难集。

Synthetic prompts 八项中，新模型在这套对抗性合成集上均持平或更高，GPT-Live-1 的 Hate 为 1.00。但 1.00 只表示该有限样本集上的评测结果，不等于现实世界“零漏检”。合成提示往往有清晰、刻意构造的风险信号；真实对话则可能包含模糊边界、更长历史和持续诱导，失败更细微。两张表都不是生产流量加权指标，也没有给出类别样本量和置信区间，跨行微小差值不应被过度解释。

安全责任还沿委派边界分层。GPT-Live 本身没有独立、广泛的工具访问，也没有代码执行能力；需要搜索、推理或 Agent 工作时会委派给后台模型。系统卡中的评测按部署形态包含委派，而委派结果继承实际执行工作的后台模型之安全训练与防护。Preparedness 结论则指出，不带委派的 GPT-Live-1/mini 在生化、AI 自我改进和网络安全跟踪类别中不太可能达到 High。故“前台模型能力较受限”不等于整个产品无高能力风险：风险和安全边界会随后台模型、可用工具、监控及账号执法共同变化。

## 落地场景、效果与经济性

适合场景的共同特征是：双手或视线被占用，任务在交谈中逐步明确，用户频繁补充条件，后台等待可由自然交谈承接。包括移动问答、驾驶辅助、语言练习、学习辅导、实时翻译、陪伴、无障碍交互、售后支持和语音驱动长任务。OpenAI 称每周有超过 1.5 亿人使用 ChatGPT Voice 和 Dictation；这是产品规模披露，不代表 GPT-Live 已有相同周活或任务成功率。

效果应分三类衡量：一是错误抢话、响应过早或过晚、有效打断恢复、backchannel 适当率、重述率和会话放弃率；二是工具选择、参数完整性、取消与最终任务完成率；三是长会话偏好、事实正确性、误导性完成声明和安全事件率。只测首包或 TTS 自然度会遗漏决定产品价值的主要失败。

GPT-Live 尚无 API 价格，不能直接计算每分钟成本。可参照但不可等同的 GPT-Realtime-2 价格为每百万音频输入 token 32 美元、输出 64 美元；2.1-mini 社区公告分别为 10 美元和 20 美元。计量方式、委派成本与产品补贴可能不同，不能据此推算 GPT-Live。

全双工会持续处理用户停顿和系统说话期间的输入，被打断输出、投机推理、预取工具、安全监控及长上下文都会增加成本；前台小模型加后台按需推理则可能避免所有音频都经过最强模型。经济性最终应以每个成功任务的推理、媒体、工具、安全和人工总成本衡量，而不是单看每分钟价格。

## 国内模型对标与差距来源

### Qwen3/3.5-Omni

[Qwen3-Omni 技术报告](https://arxiv.org/html/2509.17765v1)披露 Thinker—Talker MoE、流式多 codebook、因果 Code2Wav，以及最低 234ms 的端到端首包延迟；音频编码器使用 2000 万小时监督音频训练。这些是作者自报，不等于公网产品延迟。

Qwen3.5-Omni 进一步引入 Hybrid-Attention MoE、256K 上下文、ARIA 动态文本—语音对齐、原生 WebSearch、复杂 FunctionCall、语义打断和话权意图识别。[官方 S2S 文档](https://docs.qwencloud.com/developer-guides/speech/s2s-models)显示 Realtime Plus/Flash 支持文本、音频、图像、视频输入、函数调用与搜索，并覆盖 113 种输入语言/方言、29 种语音输出语言和 8 种中文方言。

其优势是中文、多语言、视觉和工具生态完整。待验证的是持续重叠输入下的话权稳定性，搜索和函数能否在前台持续交谈时异步完成，以及大规模真实会话中的取消、并发和错误恢复。实时 WebSocket 或流式生成不自动等于 GPT-Live 式连续全双工。

### StepAudio 2/2.5

[StepAudio 2.5 技术报告](https://arxiv.org/html/2605.23463)将 ASR、TTS 和 Realtime 视为共享音频基础模型的不同运行模式，强调任务定制 RLHF 与解码约束。较早 Step-Audio 2 披露 800 万小时真实及合成音频、语音搜索和网页搜索，但部署仍包含 VAD，说明其公开路线至少曾依赖轮次边界。

[StepAudio 2.5 Realtime 模型页](https://stepaudiollm.github.io/step-audio-2.5-realtime/)强调端到端实时语音、人设、副语言理解和表达，称从 1 万多个原创人设扩增出百万级特征矩阵，并融合数百万真实对话。其主观与客观分数、五项第一均是厂商自评，未充分披露所有竞品版本、样本和显著性，不能与 OpenAI 或其他论文分数直接相减。其中文真人感和人设后训练突出，但持续双向重叠时序及前后台并发执行仍缺少等量公开证据。

### MiniCPM-o 4.5

[MiniCPM-o 4.5 论文](https://arxiv.org/html/2604.27393)明确提出 Omni-Flow，把环境视觉、音频和模型输出置于共享时间轴，支持同时看、听、说和主动提醒。9B 模型宣称可在少于 12GB 内存的端侧设备运行。消融显示其设置下 1 秒窗口优于 0.2 和 0.1 秒，且先判断 listen/speak 再生成内容更稳定，说明全双工存在响应速度与控制稳定性的权衡。

但论文也承认全模态全双工基准有限，量化测试主要采用不含音频的 LiveSports-3K-CC，语音全双工更多依靠演示。它证明了公开架构与端侧潜力，尚不能证明长时中文交谈、噪声、工具委派及安全运营与 GPT-Live 等价。

### 差距判断

[VCB Bench](https://aclanthology.org/2026.findings-acl.1659/)以真人中文语音评估指令跟随、知识和鲁棒性，Qwen3-Omni 多项表现突出，Step-Audio 2 mini 也有竞争力。但它未同时覆盖 GPT-Live、Qwen3.5-Omni、StepAudio 2.5 和 MiniCPM-o 4.5，只能支持国内中文语音理解与知识能力已具竞争力，不能计算对 GPT-Live 的分数差。

综合证据，主要差距更可能是：连续全双工时序数据与策略；授权真实音频的训练—评测—监控闭环；前台交互与后台模型、搜索、记忆和任务状态的异步委派；情感依赖、自伤、诈骗、未成年人和模仿风险的安全运营；超大规模用户带来的在线实验和长尾反馈。国产模型在方言、中文文化、人设、表达、开源和端侧可能局部领先。以上仍是基于产品规模和系统披露的有条件结论，不是统一第三方基准排名。

## 模型厂商的投入价值、追赶路径与战略启示

对拥有基础模型、语音数据、消费入口或设备生态的模型厂商，值得投入。语音是低门槛、持续在线并可捕捉环境与情绪的 Agent 入口；全双工还会推动流式推理、多任务调度、端侧协同和在线安全。但建设目标应是“模型＋实时运行时＋任务状态＋数据闭环＋安全运营”，而不是更自然的 TTS。

较快可追赶的能力包括流式输入输出、VAD/AEC、声音与情绪控制、WebSocket 兼容、基础打断、搜索与函数接入、前导语和失败话术；中文知识、方言和本地设备噪声也可依靠本地数据形成优势。最难复制的是带准确时间戳和失败样本的真实话权数据，多任务委派中的改口、取消、恢复与结果验证，大规模设备和网络长尾，以及跨模型、媒体、客户端的安全运营。

追赶重点可压缩为七条：

1. **数据**：记录双通道音频、重叠、停顿、话权、工具状态和用户纠正；优先学习误抢话、漏打断、噪声误触发及过时结果。真人数据必须具备授权、去标识、保留和删除链路，合成数据只补稀有风险。
2. **架构**：把“是否说”与“说什么”适度解耦，支持持续输入、输出中断和任务取消；以低延迟前台控制模型配合按需后台推理，并显式识别已经陈旧的输出。
3. **Codec 与推理**：不猜测或“复刻”未公开的 OpenAI codec，而优化低 token 率、语义与韵律容量、因果解码、丢包恢复、批处理及并发；统一评估首包、实时因子、p95/p99 和成功任务成本。
4. **后训练**：奖励话权、打断恢复、口语简洁、事实性、工具状态诚实、人设和安全，而非只优化声音偏好；客服、陪伴和车载应采用不同交互规范。
5. **工具生态**：为动作设置幂等键、取消、超时、补偿和验证；语音必须区分正在查、等待确认、已经提交和外部成功，不能用流畅话术掩盖失败。
6. **安全**：开展音频原生红队和生成中监控，覆盖扰动、多人误触发、模仿、诈骗、情感依赖、自伤与未成年人，同时衡量误中断后果。
7. **评测**：分开测单轮语音智力、连续话权、带工具长任务及真实流量安全。跨厂商比较必须锁定版本、声音、设备、网络、推理和工具条件，不得把不同口径分数直接相减。

战略上，GPT-Live 应被理解为一种新运行时：交互模型负责实时共同在场，前沿模型和 Agent 负责后台工作。能否掌握两者之间的协议、数据、取消语义和安全闭环，比复制单一音频网络更决定长期竞争力。

## 风险与局限

语音的亲密感会放大情感依赖、错误信任和操纵风险；越接近真人，越应明确 AI 身份、能力和任务状态。持续监听还可能捕获旁人声音与环境敏感信息，多人场景的同意机制尤其困难，真实失败数据需求与最小采集原则存在冲突。

后台委派增加不可见性：用户未必知道由哪个模型处理、是否搜索、哪些数据进入工具、结果是否仍符合最新意图。前台流畅可能掩盖后台失败。安全介入也可能误判并突然终止对话，因此需同时评估漏检、误报、干预时机和用户后果。

经济性仍不确定。持续输入、被打断输出、并行投机、长上下文和安全监控都会增加成本，前后台分层能否抵消取决于委派频率、会话长度和缓存。GPT-Live 尚无 API 定价，无法进行可审计成本比较。

研究本身存在明显信息不对称：OpenAI 只披露功能架构和内部评测；国内最新报告多为作者或厂商自评；社区经验有选择偏差；尚无同时覆盖四个最新模型的独立真人全双工基准。因此本文结论需要随第三方评测和 API 开放持续修订。

## 核心结论

1. GPT-Live-1/mini 是 2026-07-08 发布、驱动 ChatGPT Voice 的连续全双工模型，复杂搜索、推理和 Agent 工作首发委派给 GPT-5.5；截至 2026-07-12 尚未开放 API。它不是 gpt-realtime-2/2.1、Realtime API 或 Advanced Voice Mode 的改名。
2. 关键路线是把及时自然的交谈与慢速复杂的思考执行解耦。前台管理话权、打断和在场感，后台承担深度工作，这比单纯扩大语音模型更可能成为实时 Agent 的通用架构。
3. OpenAI 未公开 GPT-Live 参数、codec、token 率和内部网络。75.7% 盲测偏好、Conversation flow 4.96 对 3.80，以及带后台委派的 GPQA、BrowseComp 和 τ³ Voice Telecom 结果，只能证明在官方设置下相对上一代改善，不能证明跨厂商绝对领先。
4. Qwen3/3.5-Omni 在多模态、语言和工具上完整；StepAudio 2/2.5 在中文真人感、人设和副语言后训练上突出；MiniCPM-o 4.5 已公开全双工时间轴和端侧实现。国内已具备有竞争力的语音智力和中文本地能力。
5. 有条件地判断，主要差距在连续全双工时序、真实交互数据闭环、后台委派与 Agent 可靠性、安全运营及大规模产品反馈，而非单一静态分数。该判断受 GPT-Live 缺少第三方测试、厂商口径不一、最新版本未被同一真人基准覆盖等限制。
6. 模型厂商值得投入，但应建设完整交互运行时。流式工程、中文场景和基础工具可较快追赶；真实话权数据、可靠委派、跨层优化和规模化安全反馈最难短期复制。
