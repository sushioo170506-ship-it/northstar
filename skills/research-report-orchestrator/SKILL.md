# Research Report Orchestrator

本 Skill 是编排器，不代替子 Skill。它负责：

- 将用户目标转换成可执行研究任务；
- 根据主题、篇幅和读者选择必要步骤；
- 向子 Skill 传递结构化中间产物；
- 在每一步执行质量卡口；
- 缺少 API、依赖或数据时降级，而不是编造结果；
- 将所有产物写入同一个可恢复的任务目录。

详细产物格式见 [`references/artifact-contract.md`](references/artifact-contract.md)，质量规则见 [`references/quality-gates.md`](references/quality-gates.md)。

## 可用子 Skill

| 能力 | Skill | 使用条件 |
| --- | --- | --- |
| 学术检索 | `academic-research-hub` | 需要论文、DOI、BibTeX、PubMed、arXiv 或 Semantic Scholar |
| 远程数据分析 | `data-cog` + `cellcog` | 存在结构化数据、已配置 `CELLCOG_API_KEY`，且资料允许上传 |
| 正文风格 | `academic-writing` | 学术、政策、技术或正式研究报告 |
| 引用规范化 | `academic-citation-manager` | 需要 APA、IEEE、GB/T 7714 等格式 |
| 静态图表 | `chart-image` | 存在可验证的结构化数值，输出 SVG/PNG |
| HTML 构建 | `kai-report-creator` | 需要自包含 HTML、主题样式或图片导出 |

不要调用带有 `Security SUSPICIOUS` 标记的第三方 Skill。当前工作流不依赖 `deep-researcher`。

## 输入

最少收集：

```yaml
topic: 研究主题
audience:
  role: 读者角色
  knowledge: beginner | intermediate | expert
length: brief | standard | deep | 自定义字数
```

建议参数：

```yaml
purpose: 读者看完后需要理解、判断或决定什么
research_type: market | academic | policy | technical | general
scope:
  regions: []
  time_range: ""
  inclusions: []
  exclusions: []
questions: []
language: zh-CN
tone: objective
citation_style: inline-link
outputs: [markdown, html]
data_files: []
sensitivity: public | internal | confidential
deadline_or_cutoff: ""
```

若只缺非关键参数，采用默认值并记录在 `00-brief.md`。只有缺失项会实质改变研究方向时，才提出不超过 3 个问题。

## 篇幅路由

| 档位 | 目标字数 | 核心问题 | 每项关键主张 | 图表 |
| --- | ---: | ---: | --- | ---: |
| `brief` | 800–1500 | 1–2 | 至少 1 个可靠来源 | 0–2 |
| `standard` | 2500–5000 | 3–5 | 尽量 2 个独立来源 | 2–5 |
| `deep` | 8000–15000 | 5–8 | 至少 2 个独立来源，并检查反证 | 4–8 |

用户指定字数时，以指定字数为准，并选择最接近的研究深度。不得通过重复内容凑字数。

## 读者路由

- 高管：先结论、影响、风险与选项，压缩方法细节。
- 投资人：市场结构、驱动因素、单位经济、关键指标和下行情景。
- 产品/业务：用户、场景、替代方案、实施约束和优先级。
- 技术专家：方法、架构、边界条件、基准和技术争议。
- 学术读者：研究问题、方法、文献脉络、证据等级和研究缺口。
- 政策读者：利益相关方、外部性、执行机制和政策权衡。
- 大众/学生：解释术语，增加背景和例子，减少缩写。

读者适配必须同时改变结构、术语、证据解释和建议，不只是改变语气。

## 执行状态

任务目录：

```text
output/<topic-slug>/
```

每完成一步，更新 `run-state.json`：

```json
{
  "stage": "outline",
  "status": "completed",
  "completed": ["intake", "outline"],
  "blocked": [],
  "degradations": [],
  "updated_at": "ISO-8601"
}
```

重试时先读取该文件，从最后一个通过质量卡口的阶段继续。不得覆盖已有中间产物；需要重做时保留旧版并添加 `.v2` 后缀。

## Step 0：任务确认与能力预检

1. 标准化输入，写入 `00-brief.md`。
2. 确定研究类型、篇幅档位、目标读者和交付格式。
3. 检查所需 Skill、二进制和环境变量。
4. 对每项数据标记敏感级别。

隐私规则：

- `confidential` 数据不得发送给 CellCog 或其他远程服务。
- `internal` 数据仅在用户明确允许上传时使用 `data-cog`。
- 若不允许上传，使用本地工具分析，并在方法部分记录降级。
- 任何密钥只能通过环境变量读取，不得写入报告或任务目录。

质量卡口：主题、读者、篇幅和研究目的明确；高风险数据已有处理策略。

## Step 1：研究问题与竞争性假说

先做最小范围扫描，再形成大纲。不要先固定一个“反常识结论”再寻找支持证据。

对每个核心问题输出：

- 2–3 个相互竞争、可证伪的假说；
- 可观测指标；
- 支持和推翻各假说所需的证据；
- 必要来源类型；
- 停止条件。

写入 `01-outline.md`，包含：

- 暂定核心判断，不得写成既定事实；
- 章节逻辑链；
- 每节的数据、案例或对比锚点需求；
- 字数预算；
- 读者可能提出的最强质疑。

质量卡口：问题可证伪；至少包含一个替代解释；章节不是话题列表。

## Step 2：并行检索与证据台账

按研究问题并行收集：

1. 一手资料：政策原文、统计、财报、标准、产品文档；
2. 学术资料：论文、系统综述、基准研究；
3. 独立二手资料：权威机构、可靠媒体、第三方测试；
4. 实景资料：用户数据、投诉、召回、公开案例。

学术检索条件满足时调用 `academic-research-hub`。检索结果必须回到原始论文或数据库记录核对，不能把搜索摘要当最终证据。

将结果写入 `02-evidence.md`。每条记录必须包含：

- 唯一 ID；
- 主张或数据；
- 来源标题、发布者、日期、URL/DOI；
- 来源类型和质量等级；
- 支持/反对哪个假说；
- 统计口径、样本和局限；
- 是否已打开原文核验。

来源等级：

- A：一手资料或方法透明的高质量同行评审研究；
- B：权威二手分析且引用链完整；
- C：可靠媒体、专家评论或尚未独立复现的资料；
- D：来源不明、营销内容、仅有摘要或无法核验。

D 级资料不得支撑关键结论。

质量卡口：关键主张达到对应篇幅的来源要求；冲突和缺口显式记录；引用可追溯。

## Step 3：数据处理与可选评分

只有存在结构化数据时才执行数据分析。只有报告确实比较多个对象，且维度可测量时才执行评分。

调用路由：

1. `CELLCOG_API_KEY` 可用且数据允许上传：可调用 `data-cog`。
2. 否则：使用本地 Python/JavaScript 分析。
3. 两条路径都不可用：保留原始数据和缺口，禁止估算补齐。

写入 `03-analysis.md`，记录：

- 清洗和转换步骤；
- 统计方法、公式和假设；
- 中间表格；
- 异常值与缺失值处理；
- 可复算结果；
- 敏感性分析。

评分规则：

- 评分维度必须服务于读者决策；
- 权重必须显式列出且总和为 100%；
- “越大越好”“越小越好”和区间最优指标使用不同归一化方向；
- 不得对序数、定性判断套用虚假精确的小数分数；
- 数据缺失不自动记 0 分，应标记缺失并说明排名偏差；
- 必须提供改变权重后的敏感性分析。

质量卡口：结果可复算；模型假设和边界明确；没有把相关性写成因果。

## Step 4：正文撰写

调用 `academic-writing` 作为风格和结构参考，但本编排器的产物格式优先。不要在最终报告外包裹 `<ama-doc>` 标签。

基于 `01-outline.md`、`02-evidence.md` 和可选的 `03-analysis.md` 写入 `04-report.md`。

每个关键段落遵循：

1. 主张；
2. 证据；
3. 解释；
4. 反证或限制；
5. 对目标读者的含义。

要求：

- 开篇先给最重要判断，不做空泛背景铺垫；
- 事实、分析和建议明确区分；
- 每个数字注明时间、单位、地区、口径和来源；
- 因果措辞与研究设计强度匹配；
- 对竞争性假说逐项给出支持、反对和置信度；
- 执行摘要可以独立阅读；
- 建议包含适用条件、优先级和风险。

质量卡口：所有关键主张能映射到证据 ID；正文与目标读者及篇幅匹配。

## Step 5：引用规范化

需要标准引用格式时调用 `academic-citation-manager`。

执行：

- 优先用 DOI、ISBN 或原始页面核验元数据；
- 统一为用户指定格式；
- 检查正文引用与参考文献一一对应；
- 删除未引用条目；
- 不得因 Crossref 返回结果而跳过与原始出版页面的核对。

更新 `04-report.md`，将检查结果写入 `05-citation-audit.md`。

质量卡口：无孤立引用、无缺失条目、无虚构 DOI、无引用错配。

## Step 6：图表

只有图表能比文字或短表更清楚地表达关系时才生成。图表数量按篇幅上限控制，不设强制最低数量。

从已核验数据生成 `06-chart-plan.md`，每张图必须包含：

- 要表达的结论；
- 数据字段和证据 ID；
- 图表类型选择理由；
- 单位、时间范围和样本；
- 来源注释。

调用 `chart-image` 输出到 `figures/`，优先 SVG。

禁止：

- 3D 图；
- 用饼图比较难以识别的细微差异；
- 截断坐标轴制造夸张差距；
- 把不确定预测画成确定事实；
- 无来源、无单位或无法回到证据台账的数据。

质量卡口：图表数字与正文一致；色盲友好；标题表达结论而非只描述图形。

## Step 7：HTML 构建

仅当 `outputs` 包含 `html` 时调用 `kai-report-creator`：

1. 将报告转换为 `.report.md` 中间表示；
2. 使用 `archetype: research`；
3. 默认选择与读者匹配的主题；
4. 要求 `--bundle`，避免交付物依赖外部 CDN；
5. 运行该 Skill 的 HTML 质量卡口；
6. 输出 `report.html`。

不得让构建阶段改写事实、数字、引用或研究结论。若构建器建议内容调整，回到 Step 4 处理。

图片导出需要 Playwright 时属于可选步骤；缺少依赖不得导致 HTML 交付失败。

## Step 8：独立终检

按 `references/quality-gates.md` 审核，写入 `07-qa.md`。

终检必须：

- 抽查最重要的 5 个事实或全部关键事实（取较多者）；
- 提出至少 3 个最强反驳；
- 检查结论是否超出证据；
- 检查不同章节数字、定义和时间口径是否一致；
- 给每项主要结论标注高/中/低置信度；
- 列出仍未解决的数据缺口。

存在一票否决问题时，不得标记完成。修复后重新执行受影响的阶段。

## 最终交付

至少返回：

- `04-report.md`
- `02-evidence.md`
- `07-qa.md`
- `report.html`（如请求）
- `figures/`（如生成）

最后向用户简要说明：

- 实际执行了哪些阶段；
- 哪些 Skill 被调用；
- 哪些步骤发生降级及原因；
- 产物路径；
- 尚未解决的限制。

不得输出内部思维过程；可以输出研究计划、证据台账、公式、检索策略和审计结果。
